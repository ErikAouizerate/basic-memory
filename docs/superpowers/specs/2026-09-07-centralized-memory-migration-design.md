# Centralized Agent Memory Migration

## Context

The Basic Memory project `main` is becoming a centralized memory shared by the user and several agents. The current knowledge base already separates domains through folders and distinguishes structured notes with `kind: fact`, but it does not explicitly distinguish episodic memories, semantic knowledge, procedures, and temporary working state.

The target is a stronger multi-agent memory model without introducing a second backend or splitting the knowledge base into several Basic Memory projects.

## Goals

- Make the four memory roles explicit and queryable.
- Keep Basic Memory as the central backend.
- Allow all agents to read the shared memory.
- Limit agent writes to raw captures, proposals, and working state by convention.
- Require human or curator validation before information becomes canonical.
- Make stale and superseded knowledge visible instead of silently competing with current knowledge.
- Keep the migration reversible and avoid unnecessary metadata.

## Non-goals

- Building a separate SQL, graph, or RAG backend now.
- Creating four Basic Memory projects or four independent indexes.
- Enforcing hard write permissions at the MCP server level.
- Rewriting every note body or preserving every historical frontmatter convention.
- Treating all notes as permanently valid facts.

## Memory model

Every managed note may use the following metadata:

```yaml
memory_class: episodic | semantic | procedural | working
lifecycle: raw | candidate | canonical | superseded | archived
source: human | agent | external
reviewed_at: 2026-09-07
valid_until: 2026-10-01
```

`memory_class`, `lifecycle`, and `source` are the core classification fields. `reviewed_at` is used when a note has been reviewed or promoted. `valid_until` is optional and is only used for knowledge that can expire. Dates use ISO-8601 calendar format.

`source` describes the origin of the information, not the writer of the Markdown file:

- `human`: information or decision supplied directly by the user.
- `agent`: content generated by an agent without an identifiable external source.
- `external`: transcript, video, article, documentation, or other outside source.

An agent may synthesize an external transcript, but the resulting note remains `source: external`. Its validation state is represented by `lifecycle`, not by changing the source.

## Existing frontmatter

The migration removes or preserves existing fields as follows:

| Field | Decision | Reason |
|---|---|---|
| `title` | Keep | Note identity and human-readable title. |
| `type` | Keep | Functional document type such as `tool`, `guide`, `policy`, `report`, `todo`, or `tracking`; it is not a memory class. |
| `kind` | Remove | Its `fact` versus informal distinction is superseded by `memory_class` and `lifecycle`. |
| `tags` | Keep, optional | Cross-cutting retrieval dimensions only; empty tag lists are removed. |
| `permalink` | Do not maintain manually | Basic Memory generates or manages it. |
| `process` | Keep only where used by `todo-agent` | It is an operational trigger, not a lifecycle state. |
| `deletable` | Keep only where used by `todo-agent` | It controls automated deletion and is not equivalent to `archived`. |
| `scope` | Keep on policies | It selects the projects or stacks to which a policy applies. |
| `url` | Keep when the note has an external URL | It stores provenance detail, not source classification. |
| `cible`, `poste`, `stack` | Keep in career notes | Domain-specific metadata with no equivalent in the memory model. |
| Existing free-form `source` values | Normalize | Values such as `transcript` or `texte de présentation — IA` are converted to the enum and their detail remains in the note body or `url`. |

The current `process` and `deletable` fields are not redundant: the self-hosted `todo-agent` actively uses them. They must not be removed from notes that participate in that workflow.

## Classification defaults

Folders provide defaults, but individual notes may override them.

| Existing area | Default memory class | Typical lifecycle |
|---|---|---|
| `devops-ia/watching/` | `episodic` | `raw` or `candidate` |
| `carriere/journal/` | `episodic` | `raw` or `canonical` |
| Raw captures in `todo/` or `devops-ia/process/` | `episodic` | `raw` |
| `tools/`, `hardware/`, `devops-ia/reports/` | `semantic` | `candidate` or `canonical` |
| `devops-ia/projects/`, `carriere/profile/`, stable career knowledge | `semantic` | `candidate` or `canonical` |
| `guidelines/`, policies, guides, skills, validated checklists | `procedural` | `candidate` or `canonical` |
| Active `todo/` items and agent scratch state | `working` | `raw` or `candidate` |

Folder placement is not an absolute truth. A raw note in `devops-ia/watching/` may be promoted into a canonical semantic or procedural note without moving the original capture.

## Lifecycle rules

- `raw`: captured content not yet reviewed; agents must not use it as authoritative truth.
- `candidate`: structured or synthesized content awaiting validation; agents may use it only when explicitly requested or clearly marked as provisional.
- `canonical`: reviewed content allowed as the current reference for normal agent work.
- `superseded`: historical content replaced by a newer canonical note or decision; retain it for traceability but exclude it from current-answer retrieval.
- `archived`: retained for historical or operational reasons and excluded from normal retrieval.

Promotion follows this default path:

```text
episodic/raw -> semantic/candidate -> semantic/canonical
episodic/raw -> procedural/candidate -> procedural/canonical
```

When a canonical fact changes, the old note or observation is marked `superseded` or the note is updated with an explicit replacement relation. The migration must not silently delete historical information.

## Multi-agent write policy

All agents may read the shared project. By convention:

- Agents may create or append `episodic/raw` notes.
- Agents may create `working/raw` or `working/candidate` state for an active task.
- Agents may propose `semantic/candidate` and `procedural/candidate` notes.
- Only the user or a designated curator agent promotes content to `canonical`.
- Agents must not rewrite or delete canonical notes without explicit authorization.
- A canonical note that becomes obsolete is marked `superseded`, not silently overwritten.

This is governance, not hard access control. All agents using the same MCP credentials can technically write to any note. Hard enforcement would require a separate write gateway, credentials, or Basic Memory projects and is outside this migration.

## Retrieval behavior

Agents must choose retrieval according to the memory class:

- Episodic: search by date, event, participants, and context; include historical states when asked about what happened.
- Semantic: prefer `lifecycle: canonical`; reject or flag expired `valid_until` values; do not merge conflicting candidates silently.
- Procedural: load active canonical policies, guides, skills, and checklists directly when the task requires them; do not treat them as ordinary historical search results.
- Working: restrict retrieval to the current task or project and avoid carrying stale working notes into unrelated tasks.

Metadata alone does not reduce context rot. The agents must use these filters and avoid loading raw captures, superseded notes, and unrelated procedures into the same context window.

## Migration sequence

1. Update the knowledge-base structure and authoring guide to replace the `kind` convention with the four memory classes and lifecycle states.
2. Define classification defaults for existing folders and exceptions for mixed folders.
3. Add the new metadata to canonical and actively used notes first.
4. Normalize existing `source` values to `human`, `agent`, or `external`; preserve details in note prose or `url`.
5. Remove `kind: fact` from migrated notes and remove empty `tags` lists.
6. Preserve `process` and `deletable` on todo-agent notes.
7. Mark clearly outdated canonical notes as `superseded` rather than deleting them.
8. Leave low-value historical captures untouched until they are next used, then classify them on demand.
9. Update agent instructions so agents write only raw/candidate content by default and ask for promotion when appropriate.

The migration should be incremental. It must not rewrite all 104 notes in one unreviewed batch, because classification errors would create a new source of silent corruption.

## Expected gains

- Fewer conflicts between current facts and historical captures.
- Safer collaboration between multiple agents.
- Clearer promotion path from capture to trusted knowledge.
- Easier exclusion of stale and irrelevant context.
- Better future export to a specialized database or retrieval pipeline.
- No immediate infrastructure migration or duplication of the whole knowledge base.

## Expected costs and losses

- Human review becomes a required step for canonical facts and procedures.
- Agents may need more targeted retrieval calls.
- Some information will exist both as a raw capture and as a curated note.
- Metadata classification can be wrong and needs occasional correction.
- Basic Memory will not enforce write permissions by itself.
- Existing ad-hoc `source` values lose their direct machine-readable detail unless that detail is moved into note prose or `url`.

## Success criteria

- Every newly created managed note has `memory_class`, `lifecycle`, and `source`.
- Canonical notes do not retain `kind: fact`.
- Existing `todo-agent` processing still works through `process` and `deletable`.
- Agents can distinguish current canonical knowledge from raw, superseded, or archived content.
- No current policy loses its `scope`, and no tool or career note loses its domain-specific metadata.
- A future backend migration can map notes by memory class and lifecycle without reinterpreting their bodies.

## Open design constraint

The migration deliberately uses metadata and agent policy rather than hard ACLs. If agents begin writing canonical notes incorrectly or if the knowledge base grows beyond reliable filtered retrieval, the next architectural step is a controlled ingestion service or separate write credentials, not more frontmatter fields.
