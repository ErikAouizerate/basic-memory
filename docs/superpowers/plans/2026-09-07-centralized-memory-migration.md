# Centralized Agent Memory Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the shared Basic Memory knowledge base to an explicit four-memory model with controlled lifecycles while preserving existing links, todo-agent behavior, and domain-specific metadata.

**Architecture:** Keep one Basic Memory project, `main`, and classify notes with `memory_class`, `lifecycle`, and normalized `source`. Keep `type`, useful tags, policy scopes, URLs, and domain-specific fields; remove the obsolete `kind` convention from migrated notes. Agents may read globally but write raw or candidate content by default, while canonical promotion remains human- or curator-controlled.

**Tech Stack:** Basic Memory MCP tools, Markdown frontmatter, existing Syncthing/todo-agent workflow, read-only filesystem inspection, `apply_patch` for configuration files.

## Global Constraints

- Modify notes under `basic-memory/` only through Basic Memory MCP tools; never edit those Markdown files directly.
- Keep `process` and `deletable` on notes consumed by `todo-agent`.
- Do not remove `scope`, `url`, `cible`, `poste`, or `stack` when they carry domain-specific meaning.
- Treat `source` as information provenance: `human`, `agent`, or `external`.
- Use `reviewed_at` only after review or promotion; use `valid_until` only for expiring knowledge.
- Do not promote the entire existing knowledge base to `canonical` without reviewing it.
- Preserve Markdown bodies, relations, URLs, and note titles during frontmatter rewrites.
- Do not create separate Basic Memory projects or a second retrieval backend.
- This workspace is not a Git repository, so implementation commits are not available.

## Metadata Contract

Managed notes use this contract:

```yaml
memory_class: episodic | semantic | procedural | working
lifecycle: raw | candidate | canonical | superseded | archived
source: human | agent | external
reviewed_at: 2026-09-07
valid_until: 2026-10-01
```

`reviewed_at` and `valid_until` are optional. The existing `title` and `type` remain. `tags` remain optional and cross-cutting. `permalink` is generated by Basic Memory and is not manually managed. `kind` is removed from migrated notes because the new contract replaces its fact/informal distinction.

  Add a short section stating that managed notes use `memory_class`, `lifecycle`, and `source`; that `reviewed_at` and `valid_until` are conditional; that `kind` is no longer used for new notes; and that agents may write raw/candidate content but require promotion for canonical content. Keep the existing prohibition on direct filesystem writes under `basic-memory/`.

- [ ] **Step 2: Replace the `kind` section in `Home — Knowledge Base Structure` through MCP**

  Use `basic-memory_edit_note` with `operation: replace_section` on the section describing the two tracks. Replace it with the four memory classes and the lifecycle meanings. Keep the existing folder map, but label folders as defaults rather than absolute classifications.

- [ ] **Step 3: Update the authoring guide through MCP**

  Use `basic-memory_edit_note` with `operation: replace_section` for the frontmatter and track sections. State the exact enum values, source provenance semantics, promotion flow, and the special rule that `process` and `deletable` remain for todo-agent notes.

- [ ] **Step 4: Read both updated notes and verify consistency**

  Run `basic-memory_read_note` for both identifiers and check that neither document instructs agents to add `kind: fact` to new notes, that the enum values match exactly, and that the direct-edit restriction remains intact.

## Task 2: Build a Bounded Migration Manifest

**Files:**
- Read: Existing notes in Basic Memory project `main`.
- Create locally during implementation: `/tmp/opencode/memory-migration-manifest.json`; remove it after migration verification.

**Interfaces:**
- Consumes: Folder defaults, note titles, current frontmatter, and the metadata contract from Task 1.
- Produces: A reviewed batch list containing each note identifier, target class, target lifecycle, target source, fields to preserve, and whether a body review is required.

- [ ] **Step 1: Enumerate notes by folder and current type**

  Use `basic-memory_list_directory` with bounded depth and `basic-memory_search_notes` for each relevant folder or type. Record the current count and note identifiers. Do not infer classifications from filenames alone.

- [ ] **Step 2: Mark governing notes as the first migration batch**

  Include `Home — Knowledge Base Structure`, the authoring guide, `basic-memory/AGENTS.md`, and the Basic Memory self-hosting report in the first batch. Mark the two knowledge-base documents as `procedural/canonical`, with `source: human` after review. Keep the self-hosting report `semantic/canonical` only after confirming its operational details; otherwise use `semantic/candidate`.

- [ ] **Step 3: Classify all remaining notes without writing them**

  Apply these defaults: `watching` and journal captures become `episodic/raw` or `episodic/candidate`; tools, hardware, reports, projects, and stable profiles become `semantic/candidate`; policies, guides, skills, and validated checklists become `procedural/candidate`; active todos and scratch state become `working/raw` or `working/candidate`.

- [ ] **Step 4: Assign source conservatively**

  Use `human` for direct user decisions or authored knowledge, `external` for transcripts, videos, articles, or documentation, and `agent` only for content generated without an identifiable human or external source. Preserve source details in the body or `url` when normalizing an old free-form `source` value.

- [ ] **Step 5: Review the manifest before any bulk write**

  Confirm that every note has a target class, lifecycle, source, and preservation list. Exclude `.trash` and `*.sync-conflict-*` files from the first migration. Stop if a note would lose a domain-specific field or a todo-agent control field.

## Task 3: Migrate Governing and Procedural Notes

**Files:**
- Modify via MCP: `guidelines/` notes, the home note, and the authoring guide.
- Modify directly: `basic-memory/AGENTS.md`.

**Interfaces:**
- Consumes: The approved manifest from Task 2.
- Produces: A trustworthy procedural layer that agents can load before performing work.

- [ ] **Step 1: Read each note completely before rewriting metadata**

  Use `basic-memory_read_note` with `output_format: json` and preserve the exact body, relations, title, directory, and relevant custom metadata. Do not derive the body from a search-result snippet.

- [ ] **Step 2: Add the new metadata without removing old keys**

  Use `basic-memory_edit_note` with `metadata` to add `memory_class: procedural`, the manifest lifecycle, `source`, and any applicable dates. This creates a reversible checkpoint before the destructive frontmatter cleanup.

- [ ] **Step 3: Rewrite frontmatter to remove `kind`**

  Because metadata merge cannot delete keys, use `basic-memory_write_note` with `overwrite: true` only after reading the full note. Pass the preserved body, title, directory, `note_type`, tags, retained custom metadata, and the new metadata. Do not include `kind`; allow Basic Memory to regenerate its permalink.

- [ ] **Step 4: Verify the procedural batch**

  Re-read every rewritten note and verify `memory_class`, `lifecycle`, and `source`; confirm relations and body content are unchanged; confirm `scope` remains on policies; and confirm no `kind` remains in the rewritten frontmatter.

## Task 4: Migrate Semantic, Episodic, and Working Notes in Reviewable Batches

**Files:**
- Modify via MCP: `tools/`, `hardware/`, `devops-ia/reports/`, `devops-ia/projects/`, `devops-ia/watching/`, `carriere/`, and `todo/` notes listed in the manifest.

**Interfaces:**
- Consumes: The classification manifest and the validated procedural rules from Tasks 1-3.
- Produces: Classified notes with no silent loss of provenance, domain metadata, or operational controls.

- [ ] **Step 1: Migrate semantic notes as `candidate` by default**

  Add `memory_class: semantic`, `lifecycle: candidate`, and a normalized `source`. Promote only notes explicitly reviewed during this batch to `canonical`, adding `reviewed_at` on promotion. Add `valid_until` only where the content has a known expiration date.

- [ ] **Step 2: Preserve tool and career metadata**

  Keep `url` on tool notes. Keep `cible`, `poste`, and `stack` on cover letters. For cover letters with a free-form `source`, normalize the frontmatter value and preserve the detailed source description in the body.

- [ ] **Step 3: Migrate captures as episodic notes**

  Mark raw videos, transcripts, journals, and unprocessed captures `memory_class: episodic`, `lifecycle: raw`, and `source: external` or `human` according to the manifest. Do not promote a capture merely because it is long or well written.

- [ ] **Step 4: Migrate active todo and agent state as working notes**

  Mark unreviewed task notes `memory_class: working`, `lifecycle: raw`; mark drafted task notes `memory_class: working`, `lifecycle: candidate`. Preserve `process: false` and `deletable: false` on every note used by `todo-agent`; never replace these fields with `lifecycle`.

- [ ] **Step 5: Remove obsolete frontmatter safely**

  For each migrated note, use the read-then-overwrite MCP procedure from Task 3 to remove `kind` and empty `tags` while preserving all fields identified as non-redundant. Do not edit files directly under `basic-memory/`.

- [ ] **Step 6: Verify each batch before starting the next**

  Re-read the batch, compare note bodies and relation counts with the manifest, and stop the batch if any title, relation, URL, custom field, or todo-agent flag changed unexpectedly.

## Task 5: Enforce Multi-Agent Retrieval and Write Behavior

**Files:**
- Modify: `basic-memory/AGENTS.md`.
- Modify via MCP: `memory://main/guidelines/basic-memory-notes-authoring-guide-for-ai-assistants`.
- Modify via MCP: `memory://main/home-knowledge-base-structure` if retrieval rules belong in the hub.

**Interfaces:**
- Consumes: The migrated metadata and lifecycle values from Tasks 1-4.
- Produces: Agent behavior that uses the classification instead of loading the whole knowledge base indiscriminately.

- [ ] **Step 1: Define retrieval rules by memory class**

  Require episodic retrieval by date/context, semantic retrieval with `lifecycle: canonical` preference and `valid_until` checks, procedural direct loading of active canonical guides/policies/skills, and working retrieval limited to the current task or project.

- [ ] **Step 2: Define write rules by lifecycle**

  State that agents may create raw captures and working state, may propose candidates, and may not promote, rewrite, or delete canonical notes without explicit authorization. Obsolete canonical knowledge becomes `superseded` rather than silently disappearing.

- [ ] **Step 3: State the permission limitation explicitly**

  Document that these are conventions because agents sharing the same MCP credentials can technically write anywhere. Do not present frontmatter as hard access control.

- [ ] **Step 4: Verify a representative retrieval matrix**

  Query one episodic, semantic, procedural, and working example with `basic-memory_search_notes` using metadata filters. Confirm that each result belongs to the expected class and that a superseded or archived note is not returned by the normal canonical query.

## Task 6: Run Migration Validation and Record Exceptions

**Files:**
- Read: All migrated notes and the migration manifest.
- Modify via MCP: Notes requiring corrected classification or missing provenance.

**Interfaces:**
- Consumes: All migrated batches and updated governance rules.
- Produces: A validated memory base and an explicit exception list for notes intentionally left unclassified.

- [ ] **Step 1: Check metadata enum validity**

  Search for values outside the allowed enums. Every managed note must have valid `memory_class`, `lifecycle`, and `source`; date fields must use `YYYY-MM-DD`.

- [ ] **Step 2: Check obsolete and duplicate fields**

  Confirm that migrated notes no longer contain `kind`. Confirm that `process` and `deletable` remain on todo-agent notes, that `scope` remains on scoped policies, and that domain-specific fields remain on career and tool notes.

- [ ] **Step 3: Check content integrity**

  Compare note bodies, relation lines, titles, and URLs before and after each batch. Investigate any difference instead of accepting a bulk rewrite blindly.

- [ ] **Step 4: Check todo-agent compatibility**

  Run the existing todo-agent test or a dry run from the self-hosted Basic Memory project. Verify that `process: true` still triggers processing, that it is reset as before, and that `deletable: true` still controls deletion.

- [ ] **Step 5: Check canonical retrieval behavior**

  Run representative searches for a current policy, a current tool, an old capture, and a superseded fact. Confirm that normal agent retrieval favors canonical content and that historical content remains available when explicitly requested.

- [ ] **Step 6: Record intentional exceptions**

  Keep a bounded list of `.trash`, sync-conflict, and notes requiring manual provenance decisions. Do not force a classification merely to reach a complete-looking count.

## Rollback Strategy

Before each rewrite batch, capture the full note content and frontmatter through `basic-memory_read_note(output_format="json")`. If verification fails, restore the affected note with `basic-memory_write_note(overwrite=true)` using the captured title, directory, body, note type, tags, and metadata. Roll back only the failed batch; do not revert unrelated user or agent changes.

## Final Verification Checklist

- [ ] Governing notes define the new metadata contract and no longer instruct new notes to use `kind: fact`.
- [ ] Managed notes use valid `memory_class`, `lifecycle`, and `source` values.
- [ ] `kind` is absent from migrated notes.
- [ ] `process` and `deletable` still work for todo-agent notes.
- [ ] `scope`, `url`, `cible`, `poste`, and `stack` are preserved where applicable.
- [ ] Canonical retrieval excludes superseded and archived notes by default.
- [ ] Raw captures remain available for historical retrieval but are not treated as current truth.
- [ ] All agents have read access, while canonical promotion remains a governed operation.
